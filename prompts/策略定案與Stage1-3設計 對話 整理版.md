## 0. 起點：策略提案的逐點分析

對話開場，使用者（子勳）帶著一份**自己構思的 12 點策略**展開討論，明確要求「先不寫 code，只談大方向」。這份策略涵蓋：年份作為 input、每年讀取當年硬規定+彈性 A、依格式決定搜尋語言類型、item 劃分與合併彈性、組合數推算、各 item 獨立抽取、違規二分法與自我驗證機制、完整性用「加總=全文」驗證、失敗案例的自我學習機制、以及「半盲測」（用早年資料訓練、測試在格式劇變年份的表現）等構想。

> **「真違規」和「抽取失敗」在觀測上是同一件事。** 使用者原策略用「文件套不進任何合法結構」偵測違規、用「部分加總不等於全文」偵測抽取失敗——但格式不統一（彈性 B）意味著一間合規公司的文件也可能切不乾淨，不是因為違規，是格式怪。這個「歸因問題」被 Claude 定調為整套流程最優先要想清楚的設計問題。

## 1. 骨架修正：加總→覆蓋、違規/格式張力、座標系與 Residual 定義

使用者針對 Claude 的回應提出多輪追問，逐步把設計釘死：

- **違規 vs 格式張力**：使用者確認「遇到失敗案例就輸出」的做法，但追問 confidence/flag 的確切定義——是否代表「有多少信心這是違規」的數值。這個提問直接推動了後續「confidence 是證據分數、非機率」的定調。
- **座標系契約**：使用者提出一個關鍵的架構問題——「char_span 是不是所有抓取 item 的聯集？如果是，能不能先定義 residual，再把 char_span 定義成全文減 residual？」並追問 residual 是否只包含封面封底，還是全文中間也會散落非 item 內容。**這個提問直接催生了後續「座標系契約」一節的最終形態**：尺（ruler）是正規化字元序列，先於 item 與 residual 存在；residual 分兩去處——尺上的 residual span、以及被剝除進 ledger 的內容。

**使用者角色：關鍵**——這幾輪提問並非單純確認 Claude 的說法，而是主動指出「residual 定義」與「char_span 定義」互相依賴的邏輯問題，逼出了整個資料契約中最基礎、也最容易被含糊帶過的一塊。

## 4. Stage 1/3 初期實作與真實 bug 修正

使用者開始在 VS Code 的 Claude Code 中實際執行，以截圖回報每一步畫面，Claude 逐一判讀「Make this edit?」（改 code，紅綠為新舊對照非錯誤）與「Allow this bash command?」（跑指令，pytest 才是真正的成績單）兩類畫面，指引使用者按哪個選項。這個階段裡使用者的角色主要是**忠實回報畫面、依 Claude 的判讀執行**，但過程中：

- 使用者主動關切離開電腦是否安全，Claude 確認這是安全的暫停點。
- 真實資料驅動出多個 bug 並在使用者核可下修正：
  - **is_geometric 幾何排除邏輯錯誤**：原本把 `reserved`/`incorporated_by_reference` item 排除於幾何集合外，違反「reserved/IBR 的標題 span 是尺上真實內容，覆蓋必須算到它，正確地空是 PASS 不是消失的理由」這條硬規則。改為只排除 `merged_into` 成員與真正無 span 的 item。
  - **頁碼誤剝**：頁首頁尾偵測原本用「數字摺疊」判斷重複，導致內容不同但都含數字的正文（如 `Unique content for section 1/2/3`）被誤判為重複頁碼而剝除。改為「逐字完全重複」或「嚴格頁碼樣式」（`_PAGENUM` 正則）雙軌判斷，並在程式碼中加註解「絕不把 item 標題當書眉剝掉」。
  - **XBRL `ix:header` 遺漏**：完整性檢查原本只認 `ix:hidden` 為 XBRL 隱藏內容，真實 MSFT 檔暴露 `<ix:header>`（包住 `ix:hidden`/`ix:references`/`ix:resources` 等機器中繼資料）也需排除，否則會被誤算入可見文字造成完整性假性 FAIL。

每次修正 Claude 都先確認診斷正確、再放行套用，套用後提醒重跑全部測試以防回歸。

## 5. README 局限分析、「有限變異分類」直覺與 XBRL 機制規則重構

Stage 1（尺）與 Stage 3（八項不變量閘門）測試達到 43 passed 全綠、核心零金鑰零網路可跑後，使用者上傳 Claude Code 的完成狀態總結，提出兩個問題：

> 「這是從自己寫的文件完成了自我測試嗎？另外，也仔細解釋這些總結，在原本的策略下應該如何理解。你應該解釋到原本策略中，方法在原則上或實務上可能有漏洞的地方。」

Claude 的回應先釐清「43 全綠」的認識論份量——代表「自己定義的檢查都通過」，不代表「抽取在真實世界一定正確」（呼應 DESIGN §5「失敗可證、成功僅被佐證」的不對稱）；再逐項對照總結內容與 DESIGN/BUILD_OPS 原則；最後**主動指出四個原設計的漏洞**：可見文字定義是不可窮盡的列舉清單（黑名單）、token 邊界在真實 HTML 中比想像脆弱、「先合成後真實」實際只驗證了一份真實檔、以及 Stage 2（真正的切割）尚未開始，目前只是把「考官」準備好、「考生」還沒進場。

**使用者角色：關鍵**——使用者隨即針對漏洞一提出一個原創的方法論問題：

> 「我同意彈性 B 的例子很有可能永遠有例外，但……有沒有可能在這一點，把所有可能的例子盡可能做有限的變異分類？」

Claude 的回應區分「有限的機制分類」（可行，把無限的具名例外收進有限的機制規則，例如「`ix:` 命名空間 ∩ 計算後不顯示」）與「窮盡列舉」（不可行，呈現層沒有規格背書，只能靠分層抽樣估計飽和度），並對照 DESIGN §5 的「完整性宣稱三層」框架（可證明封閉 / 可估計 / 不可歸約開放）。使用者決定「先重構好了」，Claude 寫出精準指令，要求：

```
把 normalize.py 裡 XBRL「不可見內容」的判斷，從「具名標籤黑名單」重構成「機制規則」：
排除 = 「ix: 命名空間」∩「計算後不顯示」（不可只看命名空間）。
關鍵反例：<ix:nonFraction>/<ix:nonNumeric> 包住可見數字，必須保留、計入守恆等式，不可排除。
新增正向反例測試防止機制規則寫過頭。
文件標明保證等級為「可估計（抽樣到飽和）」而非「可證明封閉」。
```

重構結果：45 passed（含新增的 `test_visible_ix_nonfraction_is_kept` 反例測試），機制判準改為 `_is_xbrl_excluded` 交集判斷、以白名單（`_IX_FACT_WRAPPERS`）反向判定取代黑名單。**過程中真實 MSFT 檔又逼出一個新案例**：`<ix:exclude>`（iXBRL 規格中意為「排除於 XBRL 值之外、但仍顯示給讀者」）一度被機制規則誤排除，掉了 50 個 `part`/`item` token，被守恆對帳 FAIL 抓出後修正。Claude 指出這正是漏洞一結論的活生生驗證：機制分類把問題從「無限黑名單」壓到「有限可估計」，但仍非「可證明封閉」；且失敗方向從「黑名單漏列→混入雜訊（靜默）」轉為「白名單漏列→掉字被大聲 FAIL」，是實質的穩健性提升。

## 7. 剝除的語意風險提問與 README 補完

檔案管理指令下達前，使用者對驗證報告裡一個數字提出質疑：`page_header_footer` 有 2,662 筆 ledger 記錄卻只對應 2,589 個 token，要求查清楚是否為 bug。Claude 要求 Claude Code 提供證據而非嘴上解釋，結果證實：實際 0-token 記錄有 919 筆（非原本以為的算術差 73 筆，73 只是淨值），並用**獨立於 tokenizer 的方法**（`str.isalnum()`）反向掃描全部 919 筆確認「含任何英數字元的 = 0 筆」，排除計數 bug 的可能。

**使用者角色：關鍵——提出一個原創的、觸及方法論根本的問題**：

> 「你怎麼知道那些被你剝除的符號，不會在特定語境下扮演關鍵且重要的角色（例如有或沒有那些符號，造成文字意思在法律層面上有些微但不同的差異）？」

## 8. Stage 0 設計辯論：骨架 vs 完整、動態抓取 vs 靜態表

## 9. 分層真實檔壓力測試：三個問題的發現

在確認 Stage 0 的正確定位後，使用者選擇任務優先順序：「好，現在我傾向先『加 2-3 份分層真實檔』壓力測試 stage 1/2」。Claude 寫出精準指令，要求取兩份「跨世代、刻意刁鑽」的真實 10-K（1990 年代純 ASCII、Items 1 and 2 合併的油氣公司），並嚴格要求「絕對不可為了讓新檔通過而放寬 Stage 3 任何門檻」，若一次全過需特別說明原因。

Claude Code 取得 MSFT FY1994（accession 0000891020-94-000175，純 ASCII、SGML `<TABLE>`/`<PAGE>` 包裝）與 APA Corp FY2023（accession 0001784031-24-000004，"ITEMS 1 and 2." 合併），實跑結果**兩份皆 failed，且失敗原因各異**——這是預期中理想的結果，證明刁鑽世代真的把假設逼出破綻，而非門檻被放寬。發現三個問題：

- **問題 1**：ASCII 世代被 `formats.detect_generation` 誤判為 HTML（SGML `<TABLE>` 被當 HTML 訊號），ASCII 專屬處理路徑形同死碼；完整性卻仍 CERTIFIED，正是守恆對帳「兩條路徑一致做錯」盲點的實例。
- **問題 2（最嚴重）**：density 式 TOC 偵測在 APA 深處（46%）把一串連續短 item（9B/9C + Part III IBR）誤判為 TOC，導致封面吞掉整個本體，只剩 Item 16 存活；合併驗證因此被上游 bug 完全擋住（但合併錨點本身已正確解析）。
- **問題 3**：現代 ruleset 套到 1994 舊世代，`should_exist` 誤判缺 1A/7A/9A/15（1994 年這些 item 尚未存在）——本輪確認歸類為 Stage 0 議題，不在本輪處理範圍。

## 10. 問題 2 修復：density TOC 誤判與封面吞噬

使用者將指令交給 Claude Code 之時，順帶提出一個方法論追問：「兩個獨立的方法，犯了同時的錯誤時，對帳還是會通過。那這樣我們在這次的測試中，又如何發現格式錯誤的？」Claude 的回應釐清：守恆對帳與格式判斷回答的是不同問題，格式錯誤是靠「判斷結果 vs 已知世代 ground truth」這個獨立比對抓到的，補上了守恆對帳的盲點——多個互相獨立、各補所長的檢查合起來才有意義，而非任何單一機制萬能。

Claude Code 提出問題 2 的修法：density 路徑限定「群集起點須落在 ruler 前 20%」，page-ref 路徑（點線頁碼，TOC 專屬強訊號）維持不變不受約束。使用者上傳 diff，Claude 確認修法精準（只約束真正出問題的弱啟發式，不誤傷可靠的強訊號路徑），套用後結果：58 passed（無回歸）、APA 封面正確收斂為 `[0,12526)`、22 個錨點全部進入 Stage 2。

**merged 邏輯首次在真實檔上驗證成立**：Item 1 = `status=merged` 持有整段合併 span、Item 2 = `status=merged, merged_into=1` 無獨立 span、幾何集合正確排除 Item 2、`legal_structure` 命中 `items_1_2_merged`、no_overlap/coverage 均無違反、八項不變量全 PASS、confidence=high、0 violations。使用者確認結果：「這個結果看起來有成功處理到 merged 的問題」——這是合併邏輯從「合成 fixture 驗證」升級為「真實檔驗證」的關鍵時刻。

（此階段中，使用者也主動提出對本對話過長是否影響 Claude 表現的疑慮，促成第 12 章的對話管理機制建立；因該討論性質獨立，於後面章節統一敘述。）

## 11. 問題 1 修復：ASCII 世代格式誤判

使用者要求「先寫修問題 1 的精準指令」。Claude 的指令要求把 HTML 判斷從「認 `<table>` 為訊號」改為只認真正 HTML 文件標記（`<html>`/`<body>`/`<div>`/`<font>`/`<span>`/`<!doctype html>`），並特別叮囑：**判斷問題 1 是否修好的正確判準是「格式判成 ascii + ASCII 路徑真正被執行 + 完整性走對路徑後仍 CERTIFIED」，不可用「MSFT 1994 filing_status 是否變 pass」判斷**（因為那受尚未處理的問題 3 影響，會導致誤判）。

Claude Code 修法：移除 `table` 作為 HTML 訊號，MSFT 1994 的 `div`/`font`/`span`/`p`/`body`/`html` 標記數量全為 0、只有 `<table>=60`，證明移除後必然落 ASCII。套用結果：全部測試 58 passed 無回歸，現代檔（MSFT 2023、APA 2023）逐一實測確認未被誤判為 ascii；MSFT 1994 正確判成 ascii、ASCII 專屬路徑（identity 正規化、`<PAGE>` 分頁處理）真正被執行（先前是死碼）、完整性走對路徑後仍 CERTIFIED（`missing=0/extra=0`，非先前「走錯 HTML 路徑但碰巧平衡」）。Claude Code 並主動記錄一個順帶發現（ASCII 路徑下尺內仍殘留 38 個 `<PAGE>` 字面標記，不影響完整性但語意上不精確），列為未來候選精修項，不在本輪處理範圍。

至此，分層真實檔壓力測試三個問題中，問題 1、問題 2 皆已修復並驗證無回歸，問題 3 明確歸類給 Stage 0 里程碑。
